## Goals and sessions (`git diff 8560e99 7435de5`)

1. **CONFIRMED. An approved addition is wiped when a new map that was already being drawn is approved after it.** `services/goalWorker.ts:31`, `ui/screens/goals/GoalPage.tsx:245`, `services/remap.ts:185`. "Add to this goal" is hidden and `requestAddition` refuses only while a re-map is `ready`, and `nextGoalStep` returns `'add'` even then, so both proposals can wait at once. Approving the addition, then "Use the new map", runs `applyProposal(..., { replace: true })`, which deletes every capability, the added ones included. Fix: never return `'add'` while a re-map is requested or ready (and refuse `requestAddition` while one is requested), or make `approveRemap` refuse or redraw when an addition was applied after the map was drawn.
2. **CONFIRMED. A counted free session in between drops the half-done idea of the goal's earlier planned session.** `services/session.ts:241` and `:245`. The carry looks only at `ended[0]`; a free session counted toward the goal is stored with that `goal_id`, so it comes first and `carriedPlace` returns null for it. `previouslyTaughtNodes` also makes the planned session recall the free session's ideas. Fix: filter `ended` to planned sessions (`!s.state.free`) before choosing what to carry and what to recall (design §4.5 says a counted free session's finished ideas are recalled; decide and keep the design consistent).
3. **PLAUSIBLE. A new idea from the session maker that matches an existing idea by name is taught as brand new.** `services/freeSession.ts:124` and `:245`. `resolveChoice` sets `fromDepth = 0`, `state: 'new'` and minutes before `mergeProposal` folds the idea into the existing node of the same name; if the proposal also lists that existing id, the session gets two steps with the same `nodeId` (history and `nodeStatus` collide). Fix: resolve name identities in `resolveChoice` with the existing node's depth and state, and drop duplicate steps.
4. **CONFIRMED (older than R5, made misleading by it). "Your answer did not go through. It is still in the field" is false when a later model call of the same respond fails.** `ui/screens/SessionScreen.tsx:253`; `services/session.ts` `handleTeachResponse` and `advance`. After the first call answers (the gate commits), evidence and `card`/`response` events are written; if the next idea's first card or a support card then fails, the state is not saved but those writes stay. The history gains an exchange, the draft key changes, the field comes back empty, and resending re-grades and records duplicate evidence. Fix: save the state and events up to the commit point (or buffer the writes until the respond succeeds), and say "did not go through" only when nothing was written.
5. **CONFIRMED, low. A failed session start is kept forever.** `services/sessionWork.ts:98`; `ui/components/Shell.tsx` (`work !== null`). A `start` failure has `sessionId` null, so `forget` never clears it: the sidebar's Session entry stays with "Your turn" and the Session screen shows "The session could not be planned" days later. Fix: clear a start failure once shown, when a session opens, or on dismiss.
6. **PLAUSIBLE (spec silent). A new map after an addition drops the "You added this" mark and the 1.5 weight.** `services/remap.ts:185` via `applyCompile` → `addCapabilities(..., request = null)`; `existingCapabilities` does not send the request text to the compiler. Fix: send the request text in the compile input and carry it onto matching capabilities, or keep requested capabilities through a new map.
7. **PLAUSIBLE, low. Free study makes the learner look faster.** `services/budget.ts` `planInputs` (`learnerSpeed(learned, studied)`), `services/stats.ts`. Depth gained on a goal's ideas in uncounted free sessions counts as learned; the time (surface `free`) does not count as studied. Fix: count free time on goal ideas as studied, or leave depth gained in free sessions out of learned minutes.

## Flashcards (`git diff 8560e99 a4912b9`, merged in 707840b)

1. **CONFIRMED. Cards first credited by a session use up the daily limit of new cards.** `services/cards.ts:137-139` (`firstReviewsOnScreen`) feeding `core/cards.ts` `introducedSince`. A card counts as introduced today when its first Cards-screen review is today, even if a session credit took it out of "new" earlier. Traced: 20 cards credited yesterday and reviewed on screen today, plus 5 new cards: the queue is empty and says "5 new cards wait for tomorrow". Fix: count a card only when its very first review of any source is a screen review (`s.reviews[0]?.source === 'review' ? s.reviews[0].at : null`).
2. **PLAUSIBLE. "Idea finished" fires before the session state is saved, so a failed later step runs the card writer twice for the same idea.** `services/session.ts:625` (`advance` → `onIdeaFinished` → `beginStep`). Resending after the failure finishes the idea again; near-duplicate automatic cards pass `cardKey`. Fix: collect finished ideas during `respondTo` and emit them after `saveSessionState`, or skip in `writeCardsForIdea` when auto cards already exist for that `(sessionId, nodeId)`.
3. **PLAUSIBLE, low. Goal card settings are read before the model call, not when the cards land.** `services/cards.ts:384-386` and `room()` around line 401. Lowering the maximum or turning cards off during a call still stores up to 3 cards. Fix: re-read the settings (and `enabled`) inside the write transaction.
4. **CONFIRMED by reading, low. Saving an edit wipes the All cards search, filter and open row.** `ui/screens/CardsScreen.tsx`, `<AllCards key={`${goalId}:${version}`}>` (`version` bumped in `onSaved`). Fix: drop `version` from the key; it already reloads on `cards.changed`.
5. **PLAUSIBLE, low. Review shortcuts can fire while the edit sheet is open.** `ui/screens/CardsScreen.tsx` `ignoreKey` checks `e.target.closest('dialog')`; with focus on `<body>` under an open modal, Space and 1–4 act on the card behind. Fix: also ignore keys when `document.querySelector('dialog[open]')` exists.
6. **PLAUSIBLE, low. A selection across two messages can make drafting fail.** `services/cards.ts:337` (`DraftRequestSchema`: message max 16,000, selection max 4,000) and `ui/components/QuoteReply.tsx:83` (`closest('article, section')`): the whole history section can exceed 16,000 characters and the sheet shows a raw zod error. Fix: trim the message around the selection on the server instead of rejecting.
